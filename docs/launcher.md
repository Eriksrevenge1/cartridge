# Cartridge

Cartridge, nxnative's launcher, is a Mac app that keeps your games in one library. From it you can build games, change each game's settings, mods, cheats and controls, play the Mac apps, and install the IPAs on an iPhone or iPad over USB. It writes only what each game reads by itself ([Front ends](frontends.md)), so a game you start from Finder or the Dock plays the same as from the launcher.

## Getting it

With the tools of [Build from the command line](../README.md#build-from-the-command-line) installed:

```
python3 scripts/build_launcher.py --open
```

It puts **Cartridge.app** in `/Applications`, where the Apps list shows it (`--out` names another folder), and moves a copy elsewhere, or one under its earlier name nxnative Launcher, to the Trash. Build it again after you update nxnative.

## The library

Add the folders that hold your games (the toolbar's folder button, or drag a folder onto the list). The launcher lists every nxnative Mac app in them, three folder levels deep. A controller works too: up and down pick a game, A plays it, L and R change the page.

**All Games** shows every game as a tile with its cover: click a tile to open its page, double-click it (or its Play button) to play. Search the sidebar by name or title ID, and sort by recently played, name or play time (the toolbar's sort menu). A game's cover is its own icon, the square key art the game carries, drawn as a tile as on the console; a game whose files carry no icon (a Switch 2 `.nup`, a dump folder) gets the square key art from Nintendo's store by itself, as its cover in the library and, when it is built, as its app icon (only its title ID is sent to nintendo.com); to use another picture, choose **Find Cover…** on its tile or header (right-click): the launcher looks up the game's title ID on nintendo.com (only then, and nothing else is sent) and shows the square key art Nintendo Europe has for it and the eShop's banner and screenshots, to pick one. A Switch 2 Edition has no store page of its own, so the sheet offers a web image search instead. **Choose Cover…** takes an image file, or drop one on the game's header. The launcher counts the time you play each game it starts (a game started from Finder is not counted) and shows it on the tile and the page. Settings › Library sets the appearance: System, Light or Dark. While Cartridge runs, its controller icon in the menu bar lists the five games played last (and **All Games**) to start one without the library's window, with **Console Mode** and **Open Library**; Settings › Library hides it.

Each game's page opens with its cover, name, version and play time, and **Rebuild** and **Play**, in a colour taken from the cover (the system's accent colour when the cover is mostly grey). Under them a health check says **Ready to play**, or what it found: a part of the app missing, less than 2 GB free on your home drive (where the save and caches grow), nxnative's shader translator changed since the build, or newer nxnative changes to the host, graphics, tools or the game's profile; a Rebuild takes those in. The first start of a new build or a rebuild takes longer: macOS checks the whole app before it runs, which can take a few minutes for a large game, with no window meanwhile. The page says so before that start and while it lasts (the sidebar shows *Starting…*); the game opens by itself. It has five pages:

- **Settings**: the game's settings, as its own settings window shows them ([Settings](settings.md)). A setting an `env.txt` fixes is shown greyed out. A setting you moved off the value the game was tested with is marked with a dot and shows that value, with **Use Tested** beside it. **Display › Screen** picks the screen the game opens on, listing each with its refresh rate: games run smoothest on a fixed 60, 120 or 240 Hz ([The screen](frontends.md#the-screen)).
- **Mods**: add a mod's folder (a Switch SD card's `atmosphere` folder, a folder with `romfs` in it, or the game's files themselves), turn mods on and off, and choose which wins where two change the same file. On a Switch 2 Edition whose upgrade add-on carries newer copies of the game's files (Xenoblade Chronicles: Definitive Edition), a mod made for the Switch version is carried over to those copies when you add or turn it on (data tables and settings files, by `scripts/mod_port.py`; what it did is in the mod's `PORT.txt`); images and layouts cannot be, and the page says so. Code patches (`exefs` IPS and pchtxt files for the game's own build) are applied; mods that add a code module (exlaunch, skyline) are not supported.
- **Cheats**: add an Atmosphère cheat file for the game's version (the page shows its build ID) and turn cheats on and off. Typed values and run-once cheats are set in the game's own Cheats window.
- **Controls**: for every game or for this game only. Remap a controller's buttons (or swap its sticks), rebind the keyboard, and make the mouse the camera stick: click in the game to capture the pointer, press Escape to give it back. A pair of Joy-Con 2 splits into two players when you hold SL and SR on one of them ([Pairs and singles](playing.md#switch-2-controllers-mac)).
- **Saves**: **Back Up Save…** writes the save as a `.zip`; **Restore Save…** takes one back (or a save folder), after moving the current save to the game's `save-backups` folder. Also the cloud saves folder (one folder can serve every game), the save and log folders, and the game's `env.txt`.

Changes take effect at the game's next start.

**Console mode** (the toolbar's TV button, View › Console Mode, ⇧⌘K, or a controller's Menu button) shows the library full screen for playing from the couch: a row of game tiles over the chosen game's art, with its name and play time. Left and right (the D-pad, the left stick or the arrow keys) choose a game, A or Return plays it (or brings it back, if it is running), and B, Escape, ⇧⌘K or the **Exit** button leave. A quick tap of **Home** on a controller in a game opens console mode on that game while the game goes on behind it, as the Switch's Home button does; A or Home brings it back. Home is the logo button on an Xbox or PlayStation controller; pressing View and Menu together does the same. A and B are read by their labels in Cartridge (A plays, B goes back), on every controller.

**Performance on this Mac.** After you play a game for a few minutes, the top of its **Settings** tab shows how that session ran: the frame-rate cap, how many frames were late or dropped, and how much of each frame's time the GPU used. When something should change, it suggests one setting with an **Apply** button. If frames were late, it suggests a lower render scale, MetalFX off, or a lower frame-rate cap. If there was time to spare, it suggests a higher render scale or frame rate. The numbers come from the summaries the game writes to its log every 300 frames, leaving out the first minute (loading); nothing extra runs. A raise that then does not hold is remembered and not suggested again. Settings an env file sets are left alone.

**120 fps games.** A Switch 2 game that can run at 120 fps chooses it in its own settings (often called Performance mode), and plays at 120 on a screen running at 120 Hz. Cartridge learns this the first time you play the game and then shows a **120 fps** line under Frame rate saying so (Frame rate itself only offers 30 and 60).

**Widget.** macOS runs widgets only from apps signed with an Apple developer team, so the widget is built only when you build Cartridge with `python3 scripts/build_launcher.py --sign "Apple Development: …"` (a free Apple ID makes that identity in Xcode › Settings › Accounts › Manage Certificates). Then Cartridge's **Last Played** widget (right-click the desktop › Edit Widgets…, then Cartridge) shows the game played last (small) or the last four (medium); click one to play it. Cartridge keeps its list and cover thumbnails in `~/Library/Application Support/nxnative/cartridge/`, the one folder the widget can read.

**On battery.** On a Mac laptop, a game Cartridge starts while the Mac runs on its battery gets lighter settings: 30 fps, a render scale of at most 75 %, (Settings › Battery chooses each, or turns it off). Each applies only where the game has the setting and would use more; a value set in an env file stays. Your saved settings are not changed, so on the charger the game starts as before. It is decided when the game starts, and the game's page says what it changed. (`DM_CARTRIDGE_ON_BATTERY=1` or `0` in Cartridge's environment pretends either way, for testing.)

**Screenshots.** In a game, press **Capture** (Share on an Xbox or PlayStation controller) or ⌘⇧S (Window › Take Screenshot): the frame is saved at the game's own resolution in `~/Library/Application Support/nxnative/<title ID>/Screenshots/`. A game's **Screenshots** tab shows them, newest first. Right-click one to make it the game's cover, copy, share or open it.

**Setup assistant** (Cartridge › Setup Assistant…; it opens by itself at the first start when something a build needs is missing) lists what building and playing games needs on this Mac, what it found, and a button for each thing to fix: the nxnative folder; Xcode 27.2 (it opens Apple's download page: Xcode cannot be shipped with Cartridge), its licence and first launch (asks for your password), its Metal toolchain and, for iPhone builds only, its iOS platform (all on the startup disk); Homebrew (its page) and the `xcodegen`, `zstd` and `glslang` it installs; Python 3.12 or newer for Apple silicon with the script's modules (installed into it, or into a new environment on the drive you choose, its free space checked there). Building needs your own `prod.keys` and game files: the assistant lets you point to your `prod.keys` and choose your games folder (below), and offers no way to get either.

**The engine.** Cartridge carries nxnative itself (the scripts, the host and graphics source, every game profile and the shader translator, about 710 MB) and a Python with the packing script's modules. At the first start of a new version it unpacks them beside your games folder (`.cartridge-engine/<version>`, about 860 MB; the previous version is kept, older ones removed), and every build runs from there, so building needs no nxnative checkout, no Python of your own and no `pip`. Xcode is still needed: builds compile with its compilers, which cannot be shipped. Apps it builds record the engine's commit. To build with your own nxnative checkout instead (for working on nxnative), turn off **Build with the engine Cartridge carries** in Settings › Building.

**Updates** (Settings › Updates; Cartridge › Check for Updates…): new versions of Cartridge, with their engine, come from the GitHub releases of the fork Cartridge was built from. **Stable** takes releases, **Experimental** pre-releases too. Cartridge checks once a day at its start (or never) and on **Check Now**; **Update and Restart** downloads the new version to the games folder's drive, puts the old Cartridge in the Trash and starts the new one, which unpacks its engine beside the previous one. A game built with an older engine then says so on its page: **Rebuild** (or **Rebuild All Games**) brings it up to date. Saves and settings stay. To publish a version: `python3 scripts/release_cartridge.py` (`--experimental` for a pre-release, `--dry-run` to only build and zip), with the GitHub CLI signed in and a git remote named `fork`.

**Games folder** (the setup assistant, or Settings › Library): one folder, on the drive you choose, where each game gets a folder of its own holding your game files (NSPs, a `.nup`, updates and DLC, or a dump folder), the packing script's work folders and the built app. When you build a game whose files are elsewhere, the Build window moves them in first (*Put the game's files in your games folder*, on by default); a game you built before moves in with **Move into Games Folder** in its right-click menu, which lists what moves and keeps **Rebuild** pointing at the files. On the same drive a move is instant; to another drive it is a copy, which asks first. The library always includes the folder, and folders elsewhere keep working.

## Building games

**Build Games** (the hammer) runs the packing script for you. Choose the game's files one by one: the **Base game** (an `.nsp`, `.xci`, `.nsz` or `.xcz`, or a Switch 2 game's `.nup`, which holds the whole game), its **Update** and its **DLC** (any number), each from any folder; dropping files on the window puts each in its place by the title ID in its name, and a file that looks like it belongs in another place is pointed out. At Build they are copied into a folder of their own for the game (in your games folder, else beside the base game) and built from there; your originals stay where they are, and on the same drive the copy is an APFS clone that takes no space. **Use a Folder Instead…** takes a folder holding the game's files, or a dump folder, as it is. Then build a Mac app, an IPA for iPhone and iPad, or both. NSPs need your `prod.keys`. A finished Mac app joins the library; a finished IPA is ready to install. **Rebuild** on every game's page builds it again, after a game update or a newer nxnative: from the files the launcher built it from, else from the files beside the app (its `.nup`, NSPs, dump folder or `<title ID>_build` folder, where the packing script puts the app, so a game packed from a terminal or by another front end has it too), else from the files you choose. An icon you gave a game without one of its own is kept. It is greyed out while the game runs. To add an update or DLC, choose **Add Update or DLC and Rebuild…** from the arrow beside **Rebuild** (or the game's right-click menu): the files you choose are copied into the game's NSP folder (on the same APFS drive a copy takes no space), then the game is built again. The Build Games window lists a folder's base game, updates and DLC and adds more the same way. A game built from a `.nup` or a dump folder takes its update another way, which the launcher explains. **Rebuild All Games** (hold the toolbar's hammer, or its arrow) rebuilds every game whose files are known or beside its app, one after the other, after you update nxnative; it names the games it cannot. A build does not start with less than 5 GB free on its drive, and warns below 30 GB; the Build Games window shows the free space. If the launcher was moved or nxnative lives elsewhere, set the repository folder and Python in the launcher's Settings › Building.

## Installing on an iPhone or iPad

The IPAs run on an iPhone with an A17 Pro or later and an iPad with an M1 or later. **Install on iPhone or iPad** signs an IPA with your own Apple ID and installs it over the cable:

1. Once: sign in to your Apple ID in Xcode › Settings › Accounts. The install window finds your team's ID (10 characters) by itself; if it does not, select your Apple ID there, click **Manage Certificates…**, add an **Apple Development** certificate with **+**, and click **Find**. `brew install xcodegen` if you have not.
2. Connect the device, unlock it and trust this Mac. Developer Mode must be on (Settings › Privacy & Security › Developer Mode).
3. Pick the device and the IPA and click **Install**. On the device, trust your certificate once: Settings › General › VPN & Device Management.

The first install of a game asks Xcode for a signing profile, which needs the internet. A free Apple ID works, Increased Memory Limit included (a free Personal Team was given it for [this game's iPhone test](../dm/games/010029B0118E8000/README.md)), with Apple's limits: its apps stop opening after 7 days (install again: the save and game files stay), and only a few such apps can be on a device at once. A paid developer account has neither limit. An IPA built with the game files kept out of it (`--romfs separate`) gets them copied after the install; for a large game, `brew install libimobiledevice` first. You can still use AltStore, SideStore, Sideloadly or LiveContainer instead ([Install](../README.md#install)).
